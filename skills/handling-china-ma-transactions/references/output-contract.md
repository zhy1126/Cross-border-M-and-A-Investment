# 交付物合同与完成标准

所有交付物首页必须写：事项、路由、立场、as-of 日期、材料范围/版本、关键假设、法域和完成状态。

## 1. 统一问题闭环

每个重大问题至少包含：

`事实/来源 → 待确认事实 → 法源/监管依据 → 风险事件 → 交易影响 → 主处理工具 → fallback → 买卖方立场 → 责任人/期限/证据 → 状态`

风险必须映射到价格、CP、交割交付物、陈述保证、披露、一般/特别赔偿、责任限制、过渡期承诺、终止、托管/留置或交割后整改中的一个或多个。

每个重大问题同时标注 `影响维度`：控制权、收购方式、合并财务报表中的一个或多个，并说明因果关系。纯法条查询无需虚构完整交易结构。

## 2. 结构备忘录

使用 `assets/three-axis-structure-template.md`。最低结构：

1. 交易目的、事实、假设、限制和三维执行摘要；
2. 控制权矩阵；
3. 收购方式比较矩阵：事实允许时至少三个方案，少于三个时列明其他路径及排除原因；
4. 并表支持与证据矩阵、反证、购买日候选和审计师确认包；
5. 审批、税务/会计接口、资金和签署—生效—交割—控制—购买日时间线；
6. 跨维度依赖、失败模式、恢复和 fallback；
7. 推荐方案、理由、前置事实、责任分工和完成证据；
8. 法源表（状态、pinpoint、官方链接、核验日）。

非结构类交付物只展开与请求相关的执行层，但必须说明其影响控制权、收购方式或合并财务报表中的哪些维度。并表为 `not-sought`、`not-applicable` 或 `pending-professional-confirmation` 时显式记录，不生成虚假确定结论。

## 3. 尽调与 Major Issues

使用 `assets/due-diligence-issue-list-template.md`。不能仅写“建议关注”或“由卖方承诺解决”；每项列明可核验的完成证据。完整尽调还应说明材料数量、数据室冻结时点、抽样和未覆盖实体。

## 4. 审批矩阵

使用 `assets/approval-matrix-template.md`。将签署前、效力、交割前、交割后和持续义务分开；动作动词必须与法源一致。

## 5. 谈判计划

使用 `assets/negotiation-plan-template.md`。每个议题写首选、理由、对方可能回应、让步顺序、每次 give 对应的 get、fallback 和 walk-away。不得无来源宣称“中国市场通常X%”。

## 6. 条款/文件审阅

至少输出：

- 文件地图、版本基线和跨文件定义；
- Major Issues；
- 原条款、问题、建议文本/修改方向和理由；
- 与价格、CP、保证、赔偿、披露、终止和附件的联动；
- 签署/生效/交割/登记时点冲突；
- 未核验法源、缺失附件、外国法和专业顾问接口。

如果用户要求红线或Word交付，另调用文档能力；本Skill提供实质审查，不假装已完成版式或Track Changes。

## 7. 完成状态

- `passed`：范围内闸门、法源、文件和问题闭环均满足；
- `passed_with_limitations`：可交付，但列明每一限制、影响和解除方式；
- `blocked`：缺口阻止可靠结论或实施动作，明确所需文件/决定/外部确认。

状态不是免责声明。对已知缺口仍须完成可可靠覆盖的中国法部分。

## 8. 交付前验证

1. 所有硬结论均有有效的官方法源和核验日期；
2. 草案、历史材料、案例和市场建议已分层；
3. 买方/卖方立场与首选/fallback一致；
4. 外国法、税务、会计、估值和行业技术边界可见；
5. 未公开信息、个人信息和竞争敏感信息处理符合入项闸门；
6. 重大问题均有责任人、期限、证据和状态；
7. 数字、比例、期限和定义在正文、附件和模型之间一致。
