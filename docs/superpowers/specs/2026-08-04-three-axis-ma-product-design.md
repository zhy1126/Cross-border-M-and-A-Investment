# 中国并购三维决策内核产品设计

## 1. 产品定义

本次迭代将 `handling-china-ma-transactions` 明确为一个**中国投资并购决策与执行 Skill**。它不是法规数据库、交易模板仓库或独立软件平台，而是把交易目的、事实和法律约束转化为可执行交易方案的专业工作流。

产品的核心任务是：

> 以“控制权—收购方式—合并财务报表”为三维决策内核，比较交易路径，并把选定路径落实为尽调范围、审批时间表、交易条款、谈判方案、交割步骤和失败预案。

当前版本维持纯 Skill 形态，不开发网页、后台、项目数据库、多人协作、自动法规监测或持久化案件管理。

## 2. 文章来源与产品内核

用户提供的《上市公司收购交易结构设计之核心要点解析》把控制权认定称为“起点”、收购方式称为“重点”、合并财务报表称为“靶点”。本产品吸收的是这套反向设计方法，不把文章及其旧法摘录作为现行硬法源。

三维不是三个互相孤立的专题，而是一条因果链：

1. **控制权**：先定义交易完成后买方要取得什么权力及何时取得；
2. **收购方式**：再比较通过什么工具、组合和顺序取得该权力；
3. **合并财务报表**：最后验证该结构能否形成支持预期会计处理的事实和证据。

尽调、审批、条款、谈判、签署、交割及交割后事项不是第四维；它们是使三维决策可执行的支持层。

## 3. 目标用户与核心使用场景

目标用户包括投资人、企业并购团队、律师及交易顾问。默认买方立场，用户明确要求时切换卖方立场并重做方案偏好、让步顺序和风险分配。

核心场景：

- A股上市公司控制权或潜在控制权收购；
- 非上市公司现有股权收购、控制型增资和分步收购；
- 资产、业务及 carve-out 收购；
- 围绕交易结构开展红旗尽调、协议审阅、审批规划、谈判和交割；
- 中国买方收购境外目标时的中国侧工作流。

其中 `L-CONTROL` 必须完整执行三维内核。`P-EQUITY` 和 `P-ASSET` 也必须显式处理三维，但可将某一维标记为“不追求”“不适用”“待专业确认”或“阻断”，不得静默跳过。只有经 `P-EQUITY` 筛查确认的未上市公司纯新增少数股权融资，且控制权与并表均明确为“不追求”时，才形成包含来源立场、目标审阅立场、文件版本、风险触发器和期望交付的标准交接包，再调用可选伴随能力 `$pe-vc-transaction-docs-review`；上市公司发行和资产/业务交易不走该交接，控制状态待确认时留在本 Skill 或双轨处理。如融资文件中的治理权利可能形成控制、共同控制或决定性影响，则按交接协议回调本 Skill；自动调用以当前环境已安装两个 Skill 为前提。现有股权收购、控制型增资、分步收购及与并购实质相连的少数安排仍由 `P-EQUITY` 处理。资产收购必须使用独立分支识别资产边界、经营主导权、资产收购、业务合并、同一/非同一控制及确认日/购买日，不能机械套用上市公司股东和董事标准。

## 4. 三维决策工作流

### 4.1 第一维：控制权

先记录交易目的，再建立控制权矩阵。矩阵至少区分：

- 证券监管控制；
- 公司治理控制；
- 经营者集中控制或决定性影响；
- 会计控制；
- 外资准入或安全审查口径下的实际控制。

分别计算持股、拥有权益、可支配表决权、特定会议表决权、全面摊薄比例和会计权力。记录支持事实、反证、缺失证据、取得时点和确认责任人。不得从单一持股比例、董事提名权或“不可撤销”标签直接推导控制结论。

### 4.2 第二维：收购方式

围绕第一维设定的目标比较可行结构。对于结构设计请求，在事实允许时至少给出三个方案：基准方案、主要替代方案和失败 fallback；若只有一条可行路径，应列明其他路径被排除的原因。

每个方案统一比较：

- 股份、表决权、治理和控制取得结果；
- 要约、发行、过户及信息披露路径；
- 内外部审批和法定 standstill；
- 资金、价格、税务及会计接口；
- 签署、生效、审批、交割、治理切换和购买日；
- 执行确定性、时间、成本和依赖关系；
- 单项失败后果、恢复原状可行性、替代交易和退出机制。

组合交易必须区分合同成立、合同效力与交割联动。泰胜风能案例只用于提示不必要的生效层交叉依赖可能增加监管不确定性，不能推导所有项目均须完全脱钩。

### 4.3 第三维：合并财务报表

并表分析建立从交易结构到会计证据的桥梁：

- 识别对回报产生重大影响的相关活动；
- 识别买方是否拥有现时、实质性权利；
- 评估可变回报及运用权力影响回报的能力；
- 检查其他股东否决权、独立董事、代理关系和过渡期限制等反证；
- 区分法律控制取得日、治理切换日和会计购买日；
- 形成审计师确认材料包和未决问题。

输出只可说明结构“支持”或“不足以支持”管理层评估，不得承诺并表结论。并表是硬目标时，应把审计师预沟通、治理文件、交割事实和证据交付纳入交易时间表。

## 5. 执行支持层

三维分析完成后，将每个重大问题映射到一个或多个执行工具：

- 尽调请求和关闭证据；
- 价格、支付或调整机制；
- 签约前授权、效力条件或交割条件；
- 陈述保证、披露、赔偿及责任限制；
- 过渡期承诺、终止权、long-stop 和担保；
- 审批、备案、登记、第三方同意和 standstill；
- 交割交付物、交割后行动和整合安排；
- 谈判首选、give/get、fallback 和 walk-away。

每个执行问题必须标明它服务或影响哪一维，避免产生与交易目的脱节的通用风险清单。

## 7. 输出要求

结构类交付物的固定顺序为：

1. 事项元数据及商业目标；
2. 三维执行摘要；
3. 控制权矩阵；
4. 收购方式比较及推荐；
5. 并表支持、反证和审计师确认包；
6. 尽调、审批、条款、谈判与交割行动；
7. 失败模式、fallback、责任人、期限和完成证据；
8. 分层法源表和完成状态。

非结构类请求可以只展开相关部分，但必须说明其对三维中哪些维度有影响。纯法条查询无需虚构完整交易方案。

## 8. 失败与边界处理

- 关键事实不足时，输出缺失事实、影响维度和所需证据，不伪造方案确定性；
- 并表不适用或不是交易目标时，显式记录该状态，不强行给出结论；
- 只有一个可行结构时，解释其他路径为何被排除；
- 法定禁止、审批和 standstill 不得被保证、赔偿或免责声明替代；
- 文章、案例和历史规则只生成问题及备选结构，现行法律结论仍需官方法源支持；
- 当前版本不承担外国法阈值、税务、估值或审计最终判断。

## 9. 测试与验收

实施遵循测试先行：先让新增一致性测试在现有 Skill 上失败，再写最小修改使其通过。行为评估使用当前版本作为基线，验证其是否会把三维分散处理或静默跳过；修改后用相同类型但不泄露预期答案的交易任务复测。

验收标准：

1. `SKILL.md` 明确产品定义及三维强制顺序；
2. 三维内核直接适配全部三条路由，并允许显式“不适用”；
3. 新模板可以独立形成可执行结构备忘录；
4. 尽调、审批、谈判和交割字段可回指三维；
5. 结构类输出要求至少比较三种路径或解释排除原因；
6. 会计结论保持条件式并明确审计师责任；
7. README 准确呈现产品及架构；
8. 原18项测试、法源验证、Skill一致性验证和新增测试全部通过；
9. 独立审阅未发现关键产品、法律边界或内部一致性问题；
10. GitHub `main` 与本地交付副本、个人安装副本保持一致。
