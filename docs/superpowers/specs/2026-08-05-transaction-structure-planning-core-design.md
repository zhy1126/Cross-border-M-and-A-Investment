# 交易结构方案规划核心 Skill 产品设计

## 1. 产品定义

将 `handling-china-ma-transactions` 收敛为一个**中国并购交易结构方案规划 Skill**。它根据商业目标、项目事实和硬约束形成可比较的交易路径，推荐主方案并设置备选与兜底方案，再向尽调、交易文件、审批和会计判断等后续环节输出标准化任务包。

产品不再宣称在同一 Skill 内完成全面法律尽调、整套交易文件起草或审阅、全议题谈判、审批申报、会计结论、交割管理、整合或索赔。上述工作由后续专业能力执行；本 Skill 只定义其输入任务和与交易结构相关的验收条件。

技术包名与调用名暂时保持 `handling-china-ma-transactions`，避免破坏既有安装和调用；UI 名称、描述、README 和正文改为“交易结构方案规划”。未来如需更名，另行设计迁移和兼容方案。

## 2. 核心方法

保留文章提出并经现行法与会计接口修正后的三维因果链：

1. **控制目标**：明确交易后需要取得什么权力、从何时取得，以及不同制度口径下的支持事实与反证；
2. **路径比较**：围绕控制目标比较基准、备选和兜底路径，评价步骤、约束、依赖、失败后果和恢复方案；
3. **并表证据检验**：检验路径事实能否形成支持会计控制和购买日判断的证据包，不替代管理层或会计师结论。

尽调、文件、审批和会计不是本 Skill 的并列执行模块，而是三维规划完成后的四个标准输出接口。

## 3. 固定输入接口

输入目录固定为六组；项目事实可以不同，但字段位置、缺失状态和处理规则保持稳定。

### 3.1 六组输入

1. **事项信息**：项目阶段、分析立场、法域、基准时点、保密等级、预期决策人；
2. **商业目标**：收购目的、目标权力、并表要求、预算、期限和不可牺牲目标；
3. **交易事实**：当前及拟取得股权/权益、表决权、董事会与关键经营安排、标的性质、交易对方及控制链；
4. **可选路径**：股权/股份转让、增资/发行、资产或业务收购、分步交易、间接路径及用户已有设想；
5. **硬约束**：比例上限、审批与 standstill、资金、时间、税务、上市公司、国资、外资、数据和其他不可绕过条件；
6. **材料与缺口**：已提供文件及版本、未确认事实、冲突材料、确认责任人和预计确认时间。

### 3.2 字段要求等级

每个字段只使用一个要求等级：

- `start-required`：缺失时不能启动结构化方案规划；
- `assumption-allowed`：缺失时可用明确假设继续，但必须进入待确认事项；
- `recommendation-blocker`：可以比较路径，但缺失时不得给出确定推荐，整体状态为 `blocked`。

要求等级与事实状态分开记录。事实状态固定为：

- `confirmed`：已有可定位来源支持；
- `assumed`：基于明确假设暂时采用；
- `missing`：未取得；
- `conflicting`：不同材料或陈述冲突；
- `external-confirmation-pending`：需律师、会计师、税务师、估值师或其他专业人士确认。

每一非 `confirmed` 项必须写明对方案的影响、责任人和关闭证据。

## 4. 固定分析步骤

1. 建立事项边界、立场、时点、保密和完成状态；
2. 校验六组输入，区分不能启动、可假设推进和阻断推荐的缺口；
3. 分别给控制目标、路径目标和并表目标标记状态；
4. 建立控制权与权力口径矩阵，列明支持事实、反证和取得时点；
5. 生成并比较基准、备选和兜底三条路径；若不能形成三条，列明被排除路径及原因；
6. 对每条路径执行并表证据检验，记录支持、反证、购买日候选和外部确认事项；
7. 选择推荐方案，列明成立条件、触发改道条件和决策请求；
8. 从同一结构化分析派生管理层版、律师执行版和四类后续任务包。

## 5. 固定输出接口

底层输出目录固定为八部分：

1. 项目状态及分析边界；
2. 一页式方案结论；
3. 三维目标及当前状态；
4. 基准、备选、兜底三个方案比较；
5. 推荐方案、推荐理由及成立条件；
6. 关键反证、缺失事实和待决策事项；
7. 签署—审批—交割—控制取得—并表判断时间线；
8. 后续任务包。

所有输出必须能追溯到六组输入和三维判断，不得生成与结构选择无关的通用清单。

## 6. 双版本交付

同一底层分析派生两个版本，不做两套独立判断：

### 6.1 管理层决策版

面向客户管理层、投资决策委员会或业务负责人。重点展示：

- 一页式结论；
- 三个方案的商业差异；
- 推荐理由与成立条件；
- 主要风险、反证、时间和预算影响；
- 需要管理层作出的决策及改道触发器。

不堆叠完整法条、文件审阅细节或执行清单。

### 6.2 律师执行版

面向项目律师和专业顾问。包括完整八部分输出，并保留：

- 事实来源、版本和假设；
- 控制口径和路径依赖；
- 硬法源及核验状态；
- 每项缺口的责任人、期限和关闭证据；
- 四类后续任务包及其验收条件。

两个版本的方案编号、关键事实、状态、推荐结论和时间线必须一致。

## 7. 四类后续任务包

每个任务包使用统一字段：`Package ID｜接收方｜来源方案/维度｜目的｜待核事实/待完成动作｜输入材料｜问题或指令｜责任人｜期限/阶段｜完成证据｜结果回传字段｜状态`。

### 7.1 尽调任务包

只列为了验证或排除某一结构路径必须核实的事实和材料，不生成全面尽调清单。结果回传后更新控制矩阵、路径可行性或推荐状态。

### 7.2 交易文件任务包

只列需要进入意向书、交易文件、附件或交割清单的结构安排，例如步骤联动、条件、长停日、交叉终止、失败恢复、治理切换和证据要求。不在本 Skill 内完成整套文件起草、逐条红线或全议题责任分配。

### 7.3 审批任务包

列明影响路径可行性或时点的审批、申报、备案、登记、报告、第三方同意和 standstill，分配至签署前、协议效力、交割前、交割后或持续阶段。具体申报执行由专项律师或顾问完成。

### 7.4 会计任务包

向管理层和会计师移交控制与并表判断所需事实、支持与反证、相关活动、实质性权利、可变回报、购买日候选和待确认问题。本 Skill 不出具会计结论。

## 8. 边界与完成状态

本 Skill 可以：

- 形成和比较交易结构路径；
- 推荐主方案并设置备选、兜底和改道触发器；
- 识别直接影响方案的现行中国法硬门；
- 输出结构相关的尽调、文件、审批和会计任务包。

本 Skill 不可以：

- 声称已完成全面尽调或完整交易文件审阅；
- 代替项目律师完成申报、谈判或交割管理；
- 代替会计师、税务师、估值师或外国律师作最终结论；
- 因存在模板或参考资料而宣称具备成熟的专项执行能力。

完成状态继续使用：

- `passed`：六组输入足以支持确定推荐，三维判断和任务包闭环；
- `passed_with_limitations`：推荐可以成立，但存在已披露、不会改变当前推荐的假设或外部确认；
- `blocked`：`start-required` 缺失导致无法启动，或 `recommendation-blocker` 未关闭导致不得确定推荐。

## 10. 验收标准

1. 新任务触发后首先建立六组输入，而不是直接生成全生命周期清单；
2. 每个输入字段同时具有要求等级和事实状态；
3. 缺少 `start-required` 字段时不启动，缺少 `recommendation-blocker` 字段时不作确定推荐；
4. 所有结构任务均输出基准、备选和兜底方案，或说明被排除路径；
5. 输出目录固定为八部分；
6. 管理层版和律师执行版来自同一分析，关键字段一致；
7. 四类任务包字段完整，并且只包含方案相关事项；
8. README、UI 元数据和 Skill 正文不再宣称完成全面尽调、整套文件审阅、全议题谈判、申报执行、会计结论、整合或索赔；
9. 现行硬法源、历史案例和市场观点继续分层；
10. 自动测试覆盖输入合同、输出合同、双版本一致性、任务包边界、断言禁止项和内部链接。
